# 等待消息与运行中引导

实现日期：2026-10-02；更新日期：2026-10-03。

## 交互规则

| 操作或状态 | 行为 |
| --- | --- |
| 空闲时发送 | 直接开启新轮次 |
| 运行中发送或按 Enter | 加入输入框上方的等待区，清空已提交草稿 |
| 当前轮次成功结束 | 第一条等待消息自动开启下一轮，继续按顺序发送直到队列为空 |
| 点击某条消息的“引导” | 该条消息提交到当前轮次，服务确认后从等待区移除；其余消息保持原顺序 |
| 点击移除 | 删除尚未提交的等待消息；发送中或引导确认中不能撤回 |
| 模型失败、主动停止或服务断连 | 暂停自动发送，保留等待消息；连接可用后点击“继续发送”恢复 |
| 切换任务 | 每个任务的队列独立，原任务仍可自动推进 |
| 引导时当前轮次恰好结束 | 服务返回 null，消息留在原位置，随后按队列作为新轮次处理 |

等待区保存在桌面内存中，只属于本次应用会话；退出或刷新界面后不会恢复未发送消息。已经接受的引导属于正式用户输入，保存在 SQLite，历史查询及重启后仍可读取。

## 引导如何生效

这里的“轮次”是处理一条任务到结束的执行过程，里面可能包含多次模型请求和工具执行。

引导不取消当前生成，不中止已开始的工具，也不重跑已完成操作。已经发出的 HTTP 请求不能在本地修改 input，因此消息先保存，当前完整模型响应及其全部工具结果收尾后，在下一次模型请求前加入上下文。仍使用原 turnId，已生成的内容和原任务保留；系统策略要求把引导作为当前任务的补充，除非用户明确替换或取消原任务。

即使当前模型响应没有工具调用，只要还有未处理引导，Core 也会在同一轮继续请求。每轮请求次数不设上限，也不设置应用输入或输出 Token 上限；API 返回超限错误时结束并保留输入，不自动重试。引导接受后若发生失败，不能仅凭“已接受”推断模型已处理它；`Attempt.inputThroughId` 记录每次请求实际纳入的输入边界。

参考的 [Codex Core 实现](https://github.com/openai/codex/blob/main/codex-rs/core/src/session/turn.rs) 在模型请求及工具完成后检查 pending input，在下一次采样前合并；是否继续也取决于有无 pending input。[官方 Queue/Steer 说明](https://developers.openai.com/blog/mastering-codex-remote-for-engineering) 区分等待当前工作完成后再执行的 Queue 与加入当前工作的 Steer。Tilot 采用这一轮次边界处理方式，传输仍使用现有 DeepSeek Responses HTTP/SSE。

## 实现位置

| 文件 | 职责 |
| --- | --- |
| `apps/desktop/src/input-queue.ts` | 按任务管理队列，串行启动、选择引导、移除、暂停与恢复 |
| `apps/desktop/src/workspace/pending-inputs.tsx` | 输入框上方的等待区与操作按钮 |
| `apps/desktop/src/use-chat.ts` | 把队列接到真实 RPC、历史查询及轮次事件 |
| `packages/server/src/turn-manager.ts` | 校验运行归属，保存引导并推送确认 |
| `packages/agent-core/src/run-turn.ts` | 原输入先执行，后续请求纳入当前轮次最新输入 |
| `packages/store/src/store.ts` | 保存原文及查询最新输入；版本 8 迁移仅删除旧请求次数配置，用户输入表不变 |

新增 RPC `turn.steer`：

```json
{"id":"guide-1","method":"turn.steer","params":{"turnId":"当前轮次ID","input":"补充要求原文"}}
```

非空输入被当前连接的运行中轮次接受后，返回 `TurnInput`，包含 id、turnId、content、createdAt；同时推送 `turn.input`，带 threadId、turnId、input 和连接内 seq。已结束、正在取消或不属于当前连接的轮次返回 null，不另开轮次。桌面按输入 id 合并确认与历史，不抹掉流式预览。

队列只有在服务确认后才删除消息；完成事件先于启动应答到达时，不会重复启动。轮次终态只处理一次，旧失败查询不能把用户已恢复的队列再次暂停。请求失败保留原文并暂停，用户手动继续；RPC 沿用现有协议，不增加自动重试或请求去重。

## 验证

本地测试覆盖顺序续发、后台任务、迟到应答、重复终态、失败与停止暂停、断连、旧失败查询、指定消息引导、引导结束竞态、历史合并以及等待区文本转义。Core 和 Server 测试还验证：当前请求继续完成、多个工具全部收尾后再吸收引导、配置仍冻结，以及连续引导超过原 30 次请求上限后仍在同一轮完成。

全量本地测试、全项目类型检查和前端构建已通过。按 UI 验收约定，本批没有启动原生窗口，等待区布局、鼠标点击、中文输入法和窄窗口仍需开发者验收；静态组件测试与后端联调不能替代真实窗口验收。

手动真实联调入口：

```sh
npm run test:deepseek:steering
```

仅限 Windows、Node.js 24.x；与 [已有联调脚本](deepseek-live-testing.md) 共用已保存官方默认服务配置，在独立临时数据库中复制凭据，结束后清理。会调用真实付费模型，不属于 `npm test`。

2026-10-02 使用 `deepseek-flash`、high、输出上限 4,096、当时最多 6 次请求完成以下验证。2026-10-03 已取消请求次数限制，当前真实联调脚本不再设置此项；下表保留原有真实验证结果：

| 轮次 | 输入数 | 模型请求数 | 结果 |
| --- | --- | --- | --- |
