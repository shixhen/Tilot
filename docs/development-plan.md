# Tilot 开发计划

更新日期：2026-09-19

本文记录实现顺序、每批工作边界和验收方式。产品范围以 [产品需求](./product-requirements.md) 为准，模块职责以 [技术设计](./technical-design.md) 为准，模型接入遵循 [DeepSeek 接入规范](./deepseek-integration.md)。未确认的技术选择单独列出，不作为已经确定的设计。

## 1. 开发目标和协作方式

首版完成一个可安装的 Windows 桌面 Agent：选择项目、对话、读取和搜索代码、预览并确认文件修改，以及保存和继续任务。

- 主要使用 DeepSeek，只接入 Responses API；允许用户配置 baseURL。
- 使用 OpenAI SDK，优先复用 SDK 类型，不设计通用 Provider。
- 正式历史保留完整模型输出，包括 reasoning 项及其正文。
- 只操作用户选择的项目中的代码和相关文本配置文件。
- 不加入命令执行、Git 操作、网页操作、Office、表格或文件批量整理功能。
- 每批完成一段连贯功能，通常包含几个相关函数或类型及必要测试，不再以单个简单函数作为默认停顿点。
- 单批以容易阅读和讲解为准；预计涉及多个模块的大范围改动时，先拆分，再与开发者确认。
- 每个函数、类型和接口写中文用途注释；复杂约束说明原因，不逐行翻译代码。
- 直接实现当前功能所需的正式逻辑，不写空实现、模拟业务占位或暂时绕过约束的版本；测试中的模拟不属于业务实现。
- 每批结束说明改动、关键代码、验证结果和未完成内容，等待开发者同意后进入下一批。批准本计划不等于批准一次完成全部阶段。

## 2. 已确认的目录和职责

```text
tilot/
├── apps/
│   └── desktop/
│       ├── src/          # React 界面
│       └── src-tauri/    # Tauri 桌面宿主
├── packages/
│   ├── server/           # 服务入口、模块组装、RPC 与生命周期
│   ├── agent-core/       # Agent 执行流程和状态调度
│   ├── context/          # 历史组织、上下文预算和压缩
│   ├── tool/             # 工具定义、校验、权限和执行
│   ├── store/            # 对话、配置、凭据和其他持久数据
│   ├── responses/        # SDK 客户端、流式请求和响应校验
│   └── protocol/         # UI 与 Server 共用的通信类型
└── package.json
```

不创建 runtime 包。Server 负责组装模块，Agent Core 负责业务调度。Protocol 不依赖文件系统、数据库或 SDK 客户端；UI 通过 Server 使用 Agent，不直接导入服务端实现。

内部模型数据复用 Responses 类型；UI 使用适合展示的通信数据。只有确实需要跨模块使用时才导出类型，不提前设计所有接口或建立通用框架。

## 3. 当前进度

| 内容 | 状态及边界 |
| --- | --- |
| 工程基础 | 已建立 npm workspaces、严格 TypeScript 检查和本地测试命令 |
| 包结构 | 桌面应用和七个包已建清单；多数包尚无实现 |
| 项目目录 | openWorkspace 已检查绝对路径、目录存在性并解析真实路径；尚未实现文件访问范围检查 |
| SDK 客户端 | 已支持 apiKey、可配置 baseURL、关闭 SDK 重试和禁止重定向 |
| 流式请求 | 已传递 SDK 事件，支持取消、提前结束读取和无终态断流报错；已接入序号去重、输出关联与终态一致性检查 |
| 终态响应 | 已实现 getResponseToolCalls：检查终态一致性、支持的输出内容与标识，按顺序提取成功响应中的调用；保留原始响应 |
| 验证 | 类型检查及 28 项本地测试通过；尚未进行真实模型联调 |
| 待补能力 | 工具执行、历史保存、Agent 循环、RPC、桌面界面和打包均未完成 |

现有 streamResponse 只负责一次请求的事件传递，不代表 Agent Loop 已完成，也不保证任意自定义服务都与 DeepSeek 的字段和行为一致。

## 4. 分阶段实施顺序

下表中的阶段可能包含多批代码。每批都单独讲解和确认，不将整个阶段作为一次提交规模。

| 阶段 | 主要工作 | 可观察的完成标准 |
| --- | --- | --- |
| 1. 完整模型响应 | 校验终态和输出、提取 function 调用、保留原始响应；补充事件序号和输出关联检查 | 不完整或冲突响应不会产生可执行工具调用，正常响应不丢失 reasoning |
| 2. Store 基础 | 确定存储方案；按实际需要实现配置、项目、任务、轮次、响应及工具结果的保存与查询；分开处理凭据 | 重启后可读取任务和完整模型历史，普通配置和日志不包含密钥 |
| 3. Context 基础 | 从持久记录构建 instructions 和 input，转换 SDK 历史项，校验调用与结果配对 | 多轮请求保持原始顺序，不产生孤立工具调用或丢失推理正文 |
| 4. 无工具 Agent 执行 | 实现开始、流式输出、保存成功响应、失败和取消；确定同一任务的运行互斥 | 一轮对话正确结束，失败片段不进入正式回放历史，取消后不再启动下一次请求 |
| 5. 桌面与服务贯通 | 确定 RPC 传输；实现必要协议、Server 入口、Tauri 服务进程管理和基本 React 对话界面 | 用户可配置连接、发起对话、看到流式输出并取消；桌面退出后子进程结束 |
| 6. 项目文件浏览 | 实现统一路径边界、忽略规则、文本识别、目录枚举和文件树 | UI 可选择项目并浏览允许访问的文件，目录穿越和链接越界被拒绝 |
| 7. 读取与搜索工具 | 实现文件行范围读取、文件名搜索、文本搜索，以及工具注册和参数校验 | 结果包含相对路径和行号，读取与搜索遵循同一套访问和忽略规则 |
| 8. 工具调用循环 | 将工具接入 Core，依序执行同一响应的全部调用，保存结果并构造下一次请求 | 模型可读取和搜索项目后作答；未知工具、参数错误、拒绝及取消均有配对结果 |
| 9. 修改提案与预览 | 实现文件版本记录、新建及修改提案、固定批次和差异 UI；尚不执行写入 | 用户能检查整个修改批次；提案绑定具体文件版本，模型不能自行批准 |
| 10. 确认与应用修改 | 实现批次批准、版本复核、新建冲突检查和写入结果记录 | 用户确认后应用同一批次；文件已变化时拒绝旧提案；部分失败不被报告为全部成功 |
| 11. 任务交互与恢复 | 完成任务列表、切换、重启后继续、运行中补充需求、重复提交处理和中断恢复 | 切换任务不会串流；未决写入先核对，不因重试重复应用；补充输入在明确边界生效 |
| 12. 预算和长任务 | 实现输入预算、工具结果限制、上下文摘要、最大步骤、有限重试及 usage 记录 | 压缩不拆散工具消息组；达到限制可解释地停止；缺失用量标记未知 |
| 13. 发布验证 | 构建 UI 与服务、封装 Node.js 服务进程、打包 Tauri、完成 Windows 验收 | 在没有开发环境的 Windows 机器上可安装、启动、完成文件任务并正常退出 |

阶段 5 建立早期可用的对话界面，避免所有后端完成后才检查桌面通信。真实模型联调安排在连接配置可用之后，单独记录模型、地址和测试结果，不以本地模拟结果代替兼容性验证。

基础的取消和错误处理随所属功能实现；阶段 11、12 负责多任务恢复和完整策略，不将所有异常处理推迟到最后。

## 5. 接下来三批的具体范围

### 第 1 批：成功响应校验与工具调用提取

状态：已完成。入口为 `@tilot/responses/output` 的 `getResponseToolCalls`。流式校验器已在传出终态前调用此入口验证响应；后续 Agent Core 使用该入口获取工具调用。

位置：packages/responses。

- 接收终态事件携带的完整响应，校验 status 与终态含义一致。
- 校验首版使用的消息、reasoning 和 function_call 输出，识别不支持且影响执行的输出类型。
- 按输出顺序提取工具调用，检查必要字段及 ID，不将输出项 id 与 call_id 混用。
- 返回或保留 SDK 原始响应，不将全部输出压成一条文本，不改写 reasoning。
- 工具参数在本批保持原始 arguments 字符串；具体参数 schema 和授权由 Tool 校验。

验证正常文本、混合推理与工具调用、多个调用、重复或缺失 ID、失败和截断响应。业务代码保持几个相关函数，不同时接入 Core 或数据库。

### 第 2 批：补齐流式事件一致性

状态：已完成。每次请求创建独立的 ResponseStreamValidator；重复事件去重，输出按位置及标识关联，成功终态核对已完成输出。失败和截断仍保留诊断事件，不要求补齐成功输出。

位置：packages/responses。

- 检查一次请求内的 sequence_number 顺序，相同事件可去重，冲突事件报错。
- 检查工具事件的输出位置与标识关联，正确处理多个工具交错出现的事件。
- 明确增量内容只用于预览，完整响应才是保存和后续执行的依据；done 不重复追加。
- 保留现有取消、断流和资源释放行为，不增加自动重试。

验证重复、倒序、交错、终态不一致和中途取消。尽量使用终态完整响应，避免维护另一份没有必要的完整响应副本。

### 第 3 批：Store 的第一个完整功能

位置：packages/store。

先确认存储方案和数据目录，再实现配置保存与读取，包括 baseURL、模型和应用限制。凭据存储采用单独边界；具体后端未确认前，不把密钥写入普通配置文件。其他实体等到使用时逐批添加。

验证重新打开存储后配置可恢复、无效配置不会覆盖有效配置。此批不一次性设计所有数据库表或编写整套 Store。

## 6. 在对应阶段开始前确认的事项

以下属于尚未确定的实现或产品选择；先保留问题，不阻碍下一批 Responses 开发。

| 事项 | 待确认内容 |
| --- | --- |
| 数据持久化 | 数据库存储方式、库的选择、数据目录和迁移方式；选择时说明依赖及打包影响 |
| 凭据存储 | Windows 系统凭据设施或其他方案，以及 Node.js 服务如何获取凭据 |
| RPC 传输 | Tauri 与 Node.js 服务之间采用标准输入输出或本地网络通信；需同时考虑事件流和进程退出 |
| 文本文件 | 支持的文件编码、换行保留方式、大小上限及二进制识别规则 |
| 忽略与搜索 | 遵循哪些忽略文件，是否允许用户覆盖默认忽略，以及搜索模式和结果数量限制 |
| 写入失败 | 批次发生部分失败时如何展示、是否回滚、恢复前如何核对已经写入的文件 |
| 运行中补充需求 | 输入在哪个执行边界加入、遇到待确认修改时如何处理，以及是否允许多个任务并行 |
| Skills 与 MCP | 技术设计包含这些能力，产品范围尚未明确其首版入口、来源和权限；确认后追加具体批次，不能借此引入范围外工具 |

技术设计中的 shell、GitHub 和数据库工具示例不自动变为产品需求。接入规范中的“五个 function 工具”也不等于已有五个确定的接口，工具名称与拆分在对应批次确认。

## 7. 验证和完成标准

每批按改动验证，避免只检查代码能否运行：

- 类型或实现有改动时运行类型检查；涉及响应、路径、写入、取消或状态转换时增加对应行为测试。
- 模型协议使用本地事件样本测试，文件行为使用临时项目测试；另行进行少量真实模型联调。
- 模拟数据只存在于测试中，正式功能不返回假成功或示例工具结果。
- 增加桌面功能后验证实际界面、通信和服务进程退出，不能仅以组件测试代替。
- 首版最终验收覆盖“打开项目 → 搜索和读取 → 生成修改提案 → 查看差异 → 确认应用 → 重启继续”。
- 对路径越界、外部修改冲突、断流、取消、写入部分失败和进程退出逐项验证。
- 只更新实际完成的进度，不将包目录存在、类型定义完成或测试替身通过视为功能已交付。

下一次经开发者确认后，从第 5 节的第 3 批继续；先讨论 Store 的存储方案、数据目录和凭据边界，再编写对应代码。
